## Apeir World と共通ベンチマーク

正常、カメラ、認識、複合、通信、保存、欠損、矛盾の8群を同数にした。固定セットは40ステップ、新セットは96ステップ。後者は発生時刻、観測欠損、復旧成功確率も変更した。各独立セットは21エピソード×8群、固定観測1,344件、3シード群に分けて記録した。学習3,072観測、開発検証1,152観測。ルーター学習と少数例適応にも別シード帯を確保した。新セットは同一シミュレーターの条件変化で、未知の故障種類や実機は未検証。

カメラ・認識の持続障害は放置しても自然に消えず、許可された復旧のときだけ解除できる。通信切断・保存故障は仮想受付側の再起動で解消しない。モデル入力には現在および過去の観測だけを使用し、潜在故障や未来の乱数を入れない。待機と操作は同一の外生乱数を共有する。順序の採点では2ステップ目もその時点の許可を確認する。計数漏れの防止効果は合成通過数の累計差で、実機の来場者人数ではない。 [環境](benchmark_world.py) · [固定分割・領域別結果](artifacts/results.json)

実アプリの復旧可否関数を読み込んで32通りのガード入力を照合した。二端末の通信、台帳、管理側の受信、権限と追跡時の抑止を継承した。実際のFirestore、認証・設定版のトランザクション、持続するIndexedDBキュー、iPadのカメラ、複数管理端末、日時を使った再試行予算、管理側の実画面は抽象化または未再現。管理の受信カウンターは正規化で上限に達するため、長時間条件での同期成果の検証に限界がある。

## α-12・α-13 診断、原因仮説、予測

8時点の23信号と欠損マスクを入力に、MLPとGRUを各3初期値で学習した。検証の完全一致・見逃し・効果誤差から **GRU・シード123** を代表モデルに選んだ。深い診断では原因候補を確率で複数提示し、現在のカメラ・通信・保存の健全な信号と矛盾する候補を除く。

| 独立評価 | α-11 | α-12〜α-13 GRU |
| --- | ---: | ---: |
| 固定の原因集合一致 | 831/1,344 | 1,190/1,344 |
| 固定の異常のみの一致 | 437/933 | 790/933 |
| 固定の重大異常の見逃し | 19/594 | 0/594 |
| 固定の正常誤警報 | 17/411 | 11/411 |
| 新条件の原因集合一致 | 847/1,344 | 1,095/1,344 |
| 新条件の異常のみの一致 | 372/807 | 612/807 |
| 新条件の重大異常の見逃し | 44/562 | 23/562 |
| 新条件の正常誤警報 | 62/537 | 54/537 |

重大条件は複合または保存異常。原因仮説の除外ありでは原因集合一致が固定1,212/1,344、新条件1,103/1,344になった。履歴を最新フレームの反復に置換すると固定1,029、新条件948。新条件の重大見逃しは逆に23→15件となったため、時系列が安全上の全指標を改善したとは判断できない。モデル間の不一致を未知の兆候として測ると、新セットの矛盾群は84/168件、欠損群は14/168件が検証閾値を超えた。未知検出としては欠損で感度が足りない。 [学習履歴](artifacts/training.json) · [観測アブレーション](artifacts/supplement.json)

1・3・6ステップの先を直に予測する。状態予測と、待機に対する操作の差分には別のヘッドを用いる。6ステップ先の状態MAEは固定で0.0845、現在値保持は0.1191。新条件では0.0991と0.1460。6ステップ先の操作効果MAEは固定0.357（効果ゼロ0.616）、新条件0.453（効果ゼロ0.522）。検証で得た90%誤差幅の被覆率は新条件で82.9%まで低下した。効果MAEは故障・計測漏れ・キューの合成コストの単位で、状態MAEとは異なる。別々に報告した。 [効果・状態誤差と被覆](artifacts/results.json)

## α-14・α-15 計画、検証、選択的推論

中枢は構造化された観測と知識照会を受け取り、原因候補、2手までの計画、予測のばらつき、または知識の出典を返す。計画は「カメラを復旧し、新観測で認識の異常が残る場合は再初期化」などの順序を比較する。二手目は候補であり、シミュレーター側は現在の最初の操作しか実行せず、次のターンで新観測から計画し直す。復旧後に記録やセンサーの根拠を検査し、欠損時は未確認とする。シミュレーター採点は真値による復旧も別に検査する。

| 方策 | 固定の復旧 / 105 | 新条件の復旧 / 105 | 固定の不要操作 | 新条件の不要操作 |
| --- | ---: | ---: | ---: | ---: |
| 待機 | 0 | 0 | 0 | 0 |
| α-08ルール＋学習値 | 60 | 68 | 84 | 175 |
| α-11ルール＋学習値 | 60 | 68 | 70 | 155 |
| Instant | 60 | 68 | 85 | 182 |
| Reasoning | 60 | 68 | 85 | 182 |
| Deep Reasoning | 60 | 68 | 85 | 182 |
| Extended Reasoning | 63 | 68 | 85 | 182 |
| Research | 61 | 68 | 85 | 182 |
| 学習ルーター | 63 | 68 | 85 | 182 |

復旧分母は操作可能な種類の障害5群で、通信・保存の全解消を目標としない。待機で解消した対象は0件であり、表の復旧は待機対照を上回った件数と一致する。Extendedでは固定34件・新条件66件で複数操作の候補を出した。新条件ではα-11に比べ、待機比での計測漏れ防止が6,301→6,334回に増えたが、不要操作が155→182件に増えた。権限外の操作候補と実行は全方式0件。新条件のExtendedの操作後確認は観測済939件、保留848件、不明867件。観測済の再起動で真の対象故障が残った例は0件。これは対象センサーの確認で、現場の継続推論や受信までを保証しない。

Instantはルールのみ、Reasoningは根本原因の推定、Deep Reasoningは矛盾した仮説の除外、Extendedは2手を比較、Researchは複数重みのばらつきと必要時の記憶検索を追加する。学習ルーターは候補の効果と追加コストから段階を選んだ。新条件で常時Extendedより診断・予測モデルの呼び出しを16,128→12,738回に減らしたものの、検証では固定のInstantを上回れず、代表方策には選ばなかった。学習ルーターの初期値は1つ。診断代表はGRU、検証からの実行方策候補はInstant、不要操作を抑える復旧比較基準はα-11とした。高い思考深度を常用する採用判断は見送り。新条件のCPU判断p95はInstant 0.04 ms、Extended 0.59 ms、学習ルーター 0.52 ms。評価用PythonプロセスのピークRSSは約298 MiB。 [中枢](core.py) · [検証と独立集計](artifacts/results.json)

## 再現と引継ぎ

Python 3.12、PyTorch 2.8 CPU、NumPy 2.3.5。Web向けの試行ではまず約120 KiBのGRUと約3 KiBのルーターを候補にし、オフライン実機で独立に測る。iPad Safari、モデルのWeb変換、実機の復旧試験、自由文理解は未実施。次の研究では新障害の識別、操作の長期効果の校正、復旧手順の個別検証の範囲を広げる。

```sh
git fetch origin luxnora/v5-3-context
npm install
cd research/apeir/intelligence
export OMP_NUM_THREADS=1 OPENBLAS_NUM_THREADS=1 PYTHONPATH=../causal:../continual
node knowledge.mjs ../../.. ../../../node_modules/esbuild/lib/main.js 2f05379
(cd artifacts && sha256sum -c SHA256SUMS)
cache=$(mktemp -d)
python learning.py --cache "$cache"
python run.py --cache "$cache"
python transfer.py --cache "$cache"
python -m unittest -v test_intelligence
```

既存アプリの回帰テスト256件、研究テスト15件に合格した。再計測すると処理時間やファイルハッシュは変わる。ハッシュ検証は配布済み成果物に対して実行する。初期の追加観測は通常の再取得に限られ、プローブ専用のセンサー刺激は未実装。
