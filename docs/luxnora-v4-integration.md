# Luxnora Ver.4.0 統合開発

2026-11-28 JST。正式リポジトリの main は `ebb658b`、Ver.3.0 は `dcb9b48`、Ver.3.1 は `b3b6879`。両版の変更が main に入っていなかったため、Ver.3.1 から開発を続けた。基準版の通常テスト253件、ビルド、推論独立評価8件は通過した。旧 QR-Ticket-System の main `099fb26` には Luxnora パネルとガラス風 CSS の差分がある。既存のモーション資産は同一で、今回の管理画面の追加は記憶の確認と初期化に限った。

## 実装

| 機構 | 実行経路と範囲 |
| --- | --- |
| Coreと作業記憶 | 管理画面と実行器の間にCoreを置き、文脈・スナップショット・推論・プラン・検証を接続。依存グラフ内の計算を共有し、前年読取の待機予算を依頼全体で12秒に制限。前提が変われば新しい状態で一度だけ再実行。途中結果とキューはページ内に保持。 |
| 短期・言語 | 比較と端末確認を別々の話題として5分保持。比較の時間帯だけ変更し、別のターンで端末を追加可能。参照先がない場合は確認し、イベント・運用区分・管理端末の変更で会話を引き継がない。既存の表記正規化、意図・条件の抽出、AutoのRuriを使用。 |
| 長期・経験 | 明示された処理モード、まれな再集計、前年参照の取得不可のみをブラウザ内に保存。管理端末のFirebase UIDとイベント／運用区分で分離。経験を30日で失効させ、30分以内の同じ種類を統合する。確認と初期化はパネルの支援設定から行える。以前の端末共通の処理モード値は引き継がず、各開催区分はAutoで開始する。来場者情報、画像、会話本文、人数、原因仮説は永続化しない。 |
| 知識と経験再利用 | 開催区分から台帳、端末、警告、未同期、過去の検証経験をたどる型付きのローカルグラフ。根拠の情報源・時刻・観測か報告かを保持。現在も集計不整合がある場合に限って、同じ開催区分の再集計経験を診断の案内に使う。正式な記録の正本はFirestore。 |
| 自己修正 | サーバー由来の同期済み台帳と台帳から独立に再構築したタイムラインが一致する場合、単純な全体人数の集計値を回答内で修正する。タイムライン不一致、警告、未同期、範囲付きの依頼では自動修正を適用しない。元の集計と通過記録を書き換えない。 |
| モデルと処理資源 | SwiftとAutoの双方で同じGuardとデータ検証を使う。Autoのみ未解決の読み取り依頼にRuriを遅延起動し、取消で終了、アイドル2分で解放。 |
| 受付 | 同じ、または過去に戻った時刻のフレームで検出が再入力された場合に追跡状態を更新しない。受付のオフラインシェルを更新。既存のEfficientDet Lite0、BodyPix、方向判定、保存、復旧と権限経路を継承。 |

## 仮想運営と独立評価

`npm run evaluate:luxnora:v4 -- /path/to/v3-reasoning-checkout` で再現できる。開場中の仮想運営では来場・退場の正解を観測台帳から分け、判断側に正解は渡さない。正常、古い報告、同期遅延、カメラ停止、退場漏れ、重複、集計の破損、タイムラインの破損の8構成を、時間分布と人数を変えて試した。受付側は匿名の合成座標系列で、通常、逆方向、横並び、遮蔽、同時刻の競合を比較した。各構成内の反復は独立した故障機構の数を表さない。

| 評価 | Ver.3.1 | Ver.4.0 |
| --- | ---: | ---: |
| 仮想運営の期待結果 | 336 / 384 | 384 / 384 |
| 台帳が正常な集計の破損を修正 | 0 / 48 | 48 / 48 |
| タイムラインの破損時に保留 | 48 / 48 | 48 / 48 |
| 合成通過判定 | 256 / 320 | 320 / 320 |
| 同時刻の矛盾する検出を計測しない | 0 / 64 | 64 / 64 |
| 比較と端末確認の3ターン | 1 / 3 | 3 / 3 |

基準版では、独立した台帳と時系列を検証できても全人数を保留していた。また、同じ時刻に別の位置が届くと計測線を越えたとして扱うことがあった。新しい方式は両者に限定して修正した。合成運営の所要時間はNode上のローカル処理のみ。Firestore通信、描画、モデル初期化、カメラ画像の認識精度は計測に含めていない。旧版の言語・推論セットを回帰用に使用し、今回のシナリオは開発中に使った機構別の比較である。大規模な自然言語の最終評価は未実施。

## 学習研究

Apeir α-02をCPUで学習した。4時点のテレメトリから障害の候補を分類し、最後の時点とそれ以前の少なくとも1時点で正常の根拠が揃う場合のみ正常判定を許す。学習16,000件、閾値選択2,500件、別乱数・欠損率・末尾の部分復旧を含む評価4,000件。単時点ルールとα-01には最後の1時点を、時系列ルールとα-02には同じ4時点を入力した。

| 方式 | 正答率 | 異常を正常扱い | 重み付き誤り |
| --- | ---: | ---: | ---: |
| ルール | 42.08% | 70 | 2,947 |
| 時系列ルール | 35.85% | 8 | 2,638 |
| α-01 | 57.97% | 418 | 5,443 |
| α-02 | 49.00% | 9 | 2,121 |

異常を正常扱いする誤りを10倍で評価した。α-02は重み付き誤りが最少だったが、重大誤判定だけを見ると時系列ルールの方が1件少なかった。部分復旧後の履歴でも異常を見落とすケースが残るため、研究環境に留めた。コードと重みの再生成は `OPENBLAS_NUM_THREADS=1 python3 research/apeir/train_temporal.py --output /tmp/apeir-v4`。日本語専用モデルの新規学習は行っていない。

## 回帰検証

通常テスト256/256、Firestoreエミュレーター9/9、ビルド成功。既存言語評価21/21、Ver.3.1推論評価12/12と独立8/8も通過した。Chromiumでビルド済みのRuriを実行し、初回分類は約13.4秒、次の依頼を中断した際はWorkerが1回終了した。初回分類の単発値で、iPadのレイテンシやメモリ負荷は未測定。

## 残る工程

- UI・アプリ状態を含むiPad Safari、学校Wi-Fi、オフライン再起動、8時間連続稼働、実画像での遮蔽や同時通過は未検証。端末性能を測定したうえで検出・骨格・セグメンテーション方式を比較する。
- 年度・時間帯・条件の任意の組合せ、複数解釈からの探索、経験からの予測誤差学習、復旧結果の永続記録、キュー復元、利用者ごとの端末間同期、受付での新しい自律復旧方式は未実装。
- 長期記憶は端末内の開催区分単位で、端末を共用する場合は同じFirebase UIDの範囲で共有される。権限付与に使用しない。
- 仮想環境に未見の障害構成、期間を通した状態遷移、複数ターンと非同期操作を追加してから最終精度を判定する。本番へのマージとデプロイは未実施。
