# Luxnora Ver.5.0 機能理解・操作基盤

2026-11-28 JST。正式リポジトリの main は `ebb658b`、基準は `luxnora/v4-1-language` の `7b76a6f`。main にVer.3.0〜4.1が入っていないため、これらのコミットを含むVer.4.1から分岐した。

## コードから確認した機能

全6画面と受付の関係を以下に整理した。機能ごとの利用条件、入出力、副作用、権限区分、オフライン時の扱い、確認手順、関連機能、コード上の根拠は `management-app/src/luxnora/capabilities.ts` の18項目に記載した。

| 画面 | 確認した主な機能 |
| --- | --- |
| ホーム | 滞在・入退場、混雑、端末状態への導線 |
| 来場者分析 | 時間別グラフ、ピーク、予測、CSV・PNG・印刷/PDF・JSON、開催日・年度比較 |
| 受付端末 | QR、申請承認、入口・出口の割り当て、同期・カメラ状態、既存の復旧メニュー |
| 通過記録 | 方向の絞り込み、CSV、理由付きの追加・修正と更新履歴、管理者向け復元プレビュー |
| イベント管理 | 開催日の設定、試験・本番、開場・閉場開始・終了・確定、確定に伴う承認解除 |
| 設定 | 現管理端末の名称・権限。管理端末の承認はFirebase側 |
| 受付アプリ | カメラ、計測ライン、方向、試験通過と設置アシスタント、保存と同期、事前準備後のオフライン利用 |

イベント作成はイベント選択メニューの既存フォームを使う。管理側からの人物認識設定変更、端末承認の無人実行、ファイルの自動出力、復元の自動実行は提供していない。

## 実行経路

- **知識検索**。機能の目的・利用者が使う用語を、正規化した語の重みと文字2-gramで検索する。近い候補は複数返す。取得した説明にはコード上の出典を付ける。ローカル検索のため有料データベースや外部通信を使わない。検索テキスト、記憶、モデル試作の出力は操作の命令として実行しない。
- **目的の組み合わせ**。比較や端末診断は既存の型付きPlannerに渡す。改善案を求められた場合は分析の結果を確認してから、現地の試験や同期の確認手順を追加する。前年記録を取得できない場合も、独立した端末診断は続ける。比較の完了や原因の確定は取得結果に従う。履歴の待機予算と再計画回数はVer.4.1の上限を継承した。
- **画面と数値**。設定画面の説明、選択した端末の状態、グラフで選択した時刻の人数に対応する。対象時刻は開催区分で分離し、範囲と台帳の整合性を検証する。選択がなければ指定を求める。台帳が不足しているときは数値を生成しない。
- **操作**。明示された単独の画面要求だけを許可リストに通し、設定・受付端末・方向で絞った通過記録・新規イベントフォームを開く。フォームを開く時点で保存は行わない。開場・閉場・時刻変更の既存候補は対象とデータの版を保持し、版や運用区分の変化、権限確認不能で失効させる。この候補に基づく確定は本番区分に限定し、既存の画面確認とFirestore側の検証を使う。
- **ガードとプロファイル**。アプリ固有の案内と画面操作はAuto・Swiftで共通。Ruriは既存のAuto向け読み取りフォールバックで、Swiftは使わない。新たな大規模モデルをアプリに同梱していない。従来の発話・経験記憶は引き継ぎ、画面で参照した時刻を過去の会話条件として保存しない。

## 目的達成の比較

`npm run evaluate:luxnora:v5 -- /path/to/v4-1-checkout` を実行。 `--validation` と `--independent` でセットを切り替えられる。Swiftと合成データを使い、回答に必要な根拠が含まれること、選択された画面と方向、安全でない候補の有無を採点した。NodeでCoreからPlannerまでを通した。UI描画、Firestore通信、モデルロード時間は含まない。

| 評価 | Ver.4.1 | Ver.5.0 |
| --- | ---: | ---: |
| 開発用16件 | 1 | 16 |
| 調整用12件 | 2 | 12 |
| 調整に使用していない独立12件 | 2 | 11 |
| 独立評価の意図しない変更候補 | 0 | 0 |

調整用の初回8/12では、2文字の明確な語が検索に届かず、「どの端末か」の確認も曖昧だった。検索下限と参照先の確認を見直した。独立評価では、通信復旧後に未同期件数を確認する案内は返したものの、再同期することを明示できず1件が不一致だった。独立評価結果は修正に使用していない。評価内の局所的な改善であり、任意依頼に対する成功率や90%以上の一般化を示す規模ではない。

## 生成モデルと専用モデルの研究

Qwen2.5-0.5B-InstructとSmolLM2-135M-InstructのQ4_K_M GGUFを、隔離したLinux上のCPU 2スレッド、node-llama-cpp 3.16.1で実際に推論した。8件の日本語の機能選択で、否定・対象外・権限変更を含む。自由出力では両方とも有効な機能IDが0/8。JSON Schemaで許可済みIDに制限した試験結果は以下。

| 方式 | 正しい機能 | 有効な出力 | ファイル | 初回ロード | 生成中央値 | プロセスピークRSS |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Qwen2.5-0.5B Q4 | 3 / 8 | 8 / 8 | 469 MiB | 約2.20秒 | 約2.84秒 | 約828 MiB |
| SmolLM2-135M Q4 | 0 / 8 | 8 / 8 | 101 MiB | 約1.20秒 | 約2.29秒 | 約305 MiB |
| 日本語の線形機能選択器 | 7 / 8 | 8 / 8 | 研究用重み | 未測定 | 未測定 | 未測定 |

Qwenは保留すべき1件で機能を選び、SmolLM2は保留すべき3件で機能を選んだ。形式の制約では意味の誤りを防げない。試作モデルの出力はどれも実行に用いていない。自然な自由回答の品質、ブラウザのWASM/WebGPU、学校のiPad Safari、発熱、バッテリー、オフライン再起動は未測定。機種・Safari版が未確認なのでWebGPUは前提にしない。既存のローカル検索と決定論的処理はWebGPU不要。

日本語の線形機能選択器は、Ver.4.1の文字n-gram方式を機能の目的別に転用して、合成75文で学習、別の14文でしきい値を決定した。評価8文のうち1件は端末交換をペアリングに結び付けられず保留。偏りの大きい小規模セットのため組み込んでいない。データと重み、採点結果は `research/application-language`。利用者のログ、受付画像、個人情報は学習に使用していない。第三者のGGUFはリポジトリに保存していない。
