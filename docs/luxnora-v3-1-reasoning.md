# Luxnora Ver.3.1 推論・計画・自己評価

2026-11-28 JST。正式リポジトリの `main` は `ebb658b`、Ver.3.0開発ブランチは `dcb9b48`。Ver.3.0のコミットは `main` の履歴に含まれていないため、`dcb9b48` から Ver.3.1 のブランチを作成した。基準コードの通常テスト247件とビルドは成功した。旧リポジトリ、本番データ、権限設定への変更は行っていない。

## アーキテクチャ

| 段階 | 実装 |
| --- | --- |
| Observe / Retrieve | 管理アプリのイベント・運用区分のスナップショットを使う。台帳と端末に情報源、範囲、評価時刻、分かる場合は端末報告時刻、取得状態を付ける。前年参照の条件が揃う場合にだけ既存のサーバー読取経路を使う。 |
| Understand | 既存の期限付き文脈と日本語解釈から構造化した目標を得る。Autoの意味認識は読み取り候補の補助に限る。Swiftはモデルを起動せず、同じ計画・検証経路を使う。 |
| Hypothesize / Compare | 未同期、認識停止、台帳の不整合、来場ペース上昇の仮説に、支持、反証、追加確認に必要な情報を付ける。警告時刻や未同期件数から因果や加減人数を確定しない。前年度比の差には、両方の確定本番台帳と一致する実開場時間帯が必要。計測方式と停止時間が照合できない場合、差を台帳上の値として表示する。 |
| Plan / Act | レジストリの依存関係から有向グラフを組み立てる。同じ計算を共有し、循環・複合の操作候補を拒否する。実行可能なローカル処理と最大1件の履歴読取を同じ段階で開始する。履歴がない場合は比較画面に案内し、独立した目標は継続する。データ変更は既存の明示指示の確認経路を使う。 |
| Verify | 台帳の有効行から入場・退場と時刻ごとの滞在を独立に再計算する。元の集計・タイムラインと一致しない場合に人数表示を保留する。受信した前年記録の開催日とIDを照合する。古い情報は暫定とし、同期が未確認なら混雑予測を保留する。対象時刻が閉場を越える場合は外挿しない。 |
| Adapt | 同じスナップショットでの検算を再利用し、同一依頼内の履歴も共有する。効果を追跡するため、実行結果には機能別の完了・代替の情報を持たせる。永続的な経験記憶と利用者の訂正による自動学習は次の段階。 |

単一の明確な依頼は軽量経路、複数目標や履歴読み取りは標準経路、端末と台帳を組み合わせる仮説評価は高度経路を使う。決定論的なレジストリと依存グラフを採用した。階層型タスクネットワークや状態探索を追加する前に、既存機能の入出力と権限を明示して再利用できる構造にした。ベイズ的な採点には校正用の実績が必要なため、現時点では支持・反証・欠損を直接示す。意味モデルは解釈補助として維持し、学習したApeirは研究に限定する。

## タスクと中断

実行中も最大4件を待機させられる。同じ処理モードと正規化済み本文の依頼を統合し、通常の依頼は受付順、取消は即時、中断した依頼は再開時に先頭で処理する。再開は最新のスナップショットを取得してやり直す。古い操作候補は新しい依頼が入った時点で失効する。調査中にスナップショットが変わった場合は一度検証をやり直し、さらに変わった場合は回答を保留する。履歴の読み取りは1件12秒を上限に待つ。中断・取消はRuriのWorkerを終了し、開始済みのFirestore通信はSDKの制約上完了まで残ることがある。通信結果は破棄し、その先の読取を行わない。Safariでアプリを閉じるとキューは失われる。

通常テスト253/253、Firestoreエミュレーター9/9、既存の言語評価21/21、ビルド成功。

推論の表はNode上の合成データとSwiftによる単回実行。Firestore通信・Ruri・画面描画の時間を含まない。検出率の観察例では、不整合のある人数出力、古い予測、異なる履歴IDをそれぞれ保留または代替回答に変更した。履歴取込失敗時に他の目標を継続するケースと、待機中の中断・再開を別々に回帰試験した。正しい人数・正しい操作候補を受理することも確認した。この規模では幅広い依頼に対する誤拒否率、重大誤判断率、信頼性の校正値は算出できない。

開発・検証用セットで最初に失敗したのは、取得した開催日IDが要求と異なっても前年の人数を返すケースだった。履歴読取の識別子照合を実行経路に組み込み、検証用セットは回帰用に保持した。独立セットは初回で8件が一致した。両セットの出力を `evaluation/v3-1-results/` に保存した。

Chromiumでビルド済みのRuriを1回実行し、初回分類は約8.7秒だった。次の依頼を途中で取り消すと結果はnullになり、実際のWorkerが1回終了した。iPad Safari、学校Wi-Fi、実データでの比較、オフライン再起動、長時間稼働、複数端末での実計測は未検証。

## Apeir α-01

元の重みを維持し、複数の障害・古い報告・欠損を含む新規の合成2,000件で評価した。異常を正常と判定する誤りを他の誤りの10倍として採点した。

| 方式 | 正答率 | 異常を正常と判定 | 重み付き誤り | 正常時に人へ照会 |
| --- | ---: | ---: | ---: | ---: |
| ルール | 58.2% | 0 | 836 | 238 |
| モデル | 58.0% | 319 | 3,711 | 57 |
| ルールとモデルの一致＋正常確認条件 | 53.9% | 0 | 922 | 256 |

このセットではルールが最良だった。モデルの採用判断には、模擬データの正常と障害の境界や相関の改善が必要。再学習と本番復旧への接続は今回の対象外。再評価は `python3 research/apeir/evaluate_guard.py` で実行できる。
